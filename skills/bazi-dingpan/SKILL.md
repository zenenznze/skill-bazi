# 八字定盘

## 目标

在处理具体出生信息时，先把盘排对，尤其把最容易出错的部分单独拎出来判断：

1. 优先使用问真八字网页版接口获取专业细盘
2. 问真不可访问时，允许使用本地 `sxtwl` / `lunar_python` 生成结构化兜底底稿
3. 保存排盘底稿完整信息到文件，并明确标注来源
4. 再进入节气切月、真太阳时、子时换日、候选盘验证和后续分析

这个模块只做一件事：
先生成可追溯的排盘文件，再输出候选命盘，并明确说明为何最终取某一盘。

23 点前后、早晚子时、今日明时/次日子时、出生地真太阳时可能把子时退回亥时，都属于本模块内部的“子时专项”，不再另设独立入口。

## 排盘来源优先级

正式排盘阶段按以下优先级取舍：

1. 首选问真八字网页版接口。
2. 问真接口失败、网络不可达、候选过脏或临时无法使用时，使用本地 `sxtwl` / `lunar_python` 兜底。
3. 两者结果冲突时，保留两份底稿并进入验盘，不直接硬判。

问真来源：

- 页面入口：`https://pcbz.iwzwh.com/#/paipan/index`
- 对应接口：该页面实际调用的问真八字接口

本地兜底来源：

- 四柱反推：`sxtwl.siZhu2Year(...)`
- 公历排盘：`lunar_python` 的 `Solar.fromYmdHms(...).getLunar().getEightChar()`

不得改用其他万年历、其他排盘站、手写算法或凭记忆排盘。浏览器自动化只允许用于临时确认页面和接口；
正式排盘必须使用脚本化请求或本地脚本生成数据，并保存文件。

本技能包内置脚本：

```bash
python3 scripts/bazi_chart_fetch.py --source auto --date 1990-01-01 --time 00:00 --sex male --name 命主 --output work/pcbz/19900101-0000
```

`--source auto` 会先尝试问真专业细盘；若失败，自动改用本地结构化排盘，并在 `chart.md` 来源区写明问真失败原因。

子时分诊先用：

```bash
python3 scripts/zi_hour_triage.py --date 2000-05-01 --time 23:15 --sex female --name 命主 --birthplace 四川成都 --output work/zi-hour/<case-id>
```

该脚本只生成分诊报告和候选盘命令，不替代排盘。报告中的候选盘命令仍会调用统一排盘入口，并为每个候选盘生成独立 `chart.md`。

只跑问真：

```bash
node scripts/pcbz_chart_fetch.mjs --date 1990-01-01 --time 00:00 --sex male --name 命主 --output work/pcbz/19900101-0000
```

只跑本地：

```bash
python3 scripts/local_bazi_chart_fetch.py --date 1990-01-01 --time 00:00 --sex male --name 命主 --output work/local-bazi/19900101-0000
```

如果用户给的是四柱而不是公历出生时间，先用问真网页的“四柱”功能反推候选公历日期，再选择候选日期后排盘。未指定候选编号时，默认采用中间候选，作为更偏现代常用时间范围的初始排盘：

```bash
python3 scripts/bazi_chart_fetch.py --source auto --pillars "庚辰 己丑 丁亥 丙午" --sex male --name 命主 --output work/pcbz/<case-id>
```

问真四柱反推会请求问真网页版对应的 `szbz.php` 接口，并把候选公历日期保存到 `raw/szbz.json`。
本地四柱反推会调用 `sxtwl.siZhu2Year(...)`，并把候选与采用结果保存到本地 `raw/local_lunar_python.json`、
`chart.json` 和 `chart.md`。如果有多个候选日期，必须明确列出全部候选、当前采用候选和采用理由。
用户明确指定候选编号，或后续认为时间不对时，必须按用户意见重跑。

四柱反推的精度边界：

- 四柱反推只负责定位候选公历日期和时辰，不承诺分钟级精度。
- 问真和本地反推若落在同一天、同一时辰，即视为反推一致；例如一个返回巳时起点 09:00，另一个返回巳时中点 10:00，本质都是巳时代表点。
- 反推出的 `09:00`、`10:00` 等代表时间不能当作真实出生分钟使用。
- 后续若要精确起运、交运或做真太阳时边界判断，必须使用用户提供的真实出生分钟按公历起盘。

### 本地四柱反推备选

当问真“四柱”反推接口不可用、候选过脏，或需要本地交叉校验时，可以使用
`china-testing/bazi` 关键路径封装的本地候选脚本：

```bash
python3 scripts/local_bazi_reverse_lookup.py --start 1850 --end 2030 --verify 庚辰 戊寅 己酉 辛未
```

不想安装到系统环境时，可临时运行：

```bash
uv run --with sxtwl --with lunar_python python3 scripts/local_bazi_reverse_lookup.py --start 1850 --end 2030 --verify 庚辰 戊寅 己酉 辛未
```

依赖：

```bash
pip install sxtwl lunar_python
```

这个脚本只复现两条源码路径：

- 四柱反推：`sxtwl.siZhu2Year(...)`
- 公历复核：`Solar.fromYmdHms(...).getLunar().getEightChar()`

它只允许作为“本地反推候选工具”。用它得到候选公历时间后，优先用问真生成专业细盘；若问真不可用，
则用 `scripts/local_bazi_chart_fetch.py` 生成本地结构化底稿。

已知校验例：

- 输入四柱：庚辰 戊寅 己酉 辛未
- 性别：男
- 反推范围：1850-2030
- 本地唯一候选：2000-02-21 13:00:00，北京时间
- 边界提醒：13:00 正好是未时起点；若出生地经度在 120E 以西，真太阳时可能早于 13:00，需要另排午时/未时候选盘。

问真脚本会请求问真网页版对应接口，并生成：

- `raw/szbz.json`：四柱反推公历候选日期原始响应，仅四柱反推时生成
- `raw/getbasebz8.json`：基础排盘原始响应
- `raw/getRysl.json`：人元司令原始响应
- `raw/getGZRelaction3.json`：干支关系原始响应
- `raw/getgeju3.json`：格局接口原始响应
- `chart.json`：结构化专业细盘
- `chart.md`：后续分析使用的完整排盘底稿
- `liuyue-YYYY/`：仅当后续问题精确到月份时生成，来源为问真前端流月逻辑，不属于基础排盘必跑项

本地脚本会生成：

- `raw/local_lunar_python.json`：本地库结构化原始数据
- `chart.json`：结构化本地排盘数据
- `chart.md`：后续分析使用的本地排盘底稿

本地底稿缺少问真 raw、人元司令接口和问真格局接口；如果问真恢复可用，应补跑问真专业细盘。
本地库与问真接口在起运换算细节上可能不同；两者同时可用且结果冲突时，以问真专业细盘作为正式底稿，
本地结果只作为候选和交叉校验线索。

后续所有格局、命局、大运、流年和现实用途分析，都必须先读取 `chart.md` 和必要的 `raw/` 原始响应；不能绕过文件直接凭页面印象分析。

若后续问题精确到月份，还必须保留并读取 `chart.json`，因为问真流月脚本会从中读取八字、性别、日干、vip 和 userguid：

```bash
node scripts/pcbz_liuyue_fetch.mjs --year YYYY --chart-json path/to/chart.json --gregorian-month YYYY-MM --output path/to/chart-dir/liuyue-YYYY
```

该脚本生成的 `liuyue.md` 才是月份级节气切分底稿。问真没有直接返回 12 个流月干支的后端接口；流月干支来自问真前端 source map 中的 `getYueGan`、`ly_zhi`、`_JieQiData`，神煞来自 `getliunianshensha5.php`。

`chart.md` 不是越长越好，必须把模型后续分析真正依赖的主证前置到“后续分析必读”：

- 四柱天干对应十神：年、月、日、时各自的天干与主星。
- 地支藏干对应十神：每个地支藏哪些干，分别是什么十神。
- 起运与大运：起运岁数、起运详情、交运信息、每步大运的公历起止日期和年份段。
- 流年索引：每个公历年份对应的流年干支，并按所处大运分组。

十神展示必须使用自然读法，避免符号化表达：

- 写“辛劫财”，不写“辛=劫财”。
- 写“巳藏丙七杀、庚比肩、戊偏印”，不写“丙=七杀、庚=比肩、戊=偏印”。

神煞、纳音、胎元、命宫、身宫、格局接口等可保留在低优先级附录或 raw 中，但后续分析不得让这些辅助信息盖过四柱十神、大运和流年。

## 适用场景

- 用户给出精确到分钟的出生时间，希望排盘
- 用户或当事人对“到底是前一天还是后一天”存在争议
- 同一个人出现两套或多套命盘版本，需要先定盘
- 后续要做学历、家庭、恋爱、职业、婚姻等分析，但当前基础盘未定

## 必要输入

1. 公历出生年月日，或已知四柱
2. 出生时间，尽量精确到分钟；若输入四柱，需先确认反推出的候选公历日期
3. 性别
4. 出生地点，若用户已给则用于真太阳时；若用户未给，不追问，直接按北京时间排盘并声明未做经度修正
5. 是否已知某种候选盘或争议点

## 输出目标

输出必须包含以下五项：

1. 排盘底稿文件路径，并标注来源是问真还是本地
2. 标准北京时间排盘
3. 真太阳时判断：有出生地则修正并必要时另排；无出生地则直接结论为采用北京时间，不再追问
4. 存在争议的候选盘
5. 最终采用的正式盘与采用理由

禁止只给单一结果却不说明争议点。
禁止没有排盘文件就进入后续分析。若只有本地底稿，必须说明缺少问真 raw、人元司令和问真格局接口。

## 核心方法论

### 1. 先盘后断，先定边界再下结论

八字分析最忌一上来就论性格、论职业、论婚姻。必须先确认：

- 年柱是否按节气切换，而非农历春节
- 月柱是否按节气切月，而非阴历月份
- 日柱是否存在子时换日争议
- 时柱是否需要用真太阳时修正

### 2. 最容易错的不是年份，而是晚间出生的换日问题

当出生时间落在以下区域时，必须把北京时间和真太阳时分开算：

- 23:00 前后
- 接近子时
- 地点经度与东八区中央经线 120E 偏差较大

遇到这类案例，优先执行本模块的子时专项分诊。尤其是偏西地区，真太阳时可能先把北京时间子时退回亥时，此时争议点会从“子时换日”压缩成“亥时盘与子时盘哪个更贴近现实”。

### 3. 真太阳时只解决实际时辰，不自动决定日柱必换

很多错误分析会把“真太阳时进入子时”直接等同于“日柱换到第二天”。这不完整。

因为在传统命理体系里，是否换日还取决于对子时的分法：

- 子初换日
- 夜子仍属前日、正子后属次日
- 晚子时为前日、早子时为后日

传统材料可先查本地《七修类稿》卷一“阳奇阴耦”条：`references/classics-originals/raw/七修类稿/卷一.txt`。该条提到“上半夜为今日、下半夜为明日”的夜分二段思路，只作为归日口径的书证线索，不替代排盘候选和前事验证。

所以应当区分：

- 真太阳时：解决是否入子时
- 子时分法：解决日柱到底换不换

### 4. 定盘不是靠理论站队，而是靠候选盘加前事反校验

当两种取法都有理时，不要空争。正确做法是：

1. 先列两盘或三盘
2. 再用学历、家庭、恋爱、职业、时间节点去反推
3. 看哪一盘解释力更强

## SOP

### Step 0：先查既有档案

若用户说的是“我女朋友”“我爸”“某某”这类关系称呼或已知人物，先检索既有底稿和笔记，不要直接要求用户重新给出生信息。

优先查本技能包工作目录：

```bash
rg -n "当事人姓名|女朋友|girlfriend|出生|生日|八字|四柱|chart\\.md|chart\\.json" work
find work -path '*chart.json' -o -path '*chart.md'
```

若当前环境可访问用户提供的笔记库或资料目录，再查对应人物目录和基本信息：

```bash
rg -n "当事人姓名|女朋友|出生|生日|八字|四柱|问真|chart\\.md" notes docs
```

判断规则：

- 已有问真 `chart.json/chart.md`，且姓名、出生日期或关系链能对应上：直接采用该底稿进入后续模块。
- 有北京时间盘和真太阳时盘：列出两份文件及差异；若本次问题不依赖时柱差异，可说明共同主线后继续；若依赖时柱，转 `/bazi-liunian` 验盘。
- 只有笔记记录出生信息但没有底稿：按记录信息跑问真排盘。
- 多个候选都可能是同一人：先列候选，不混盘断。

### Step 1：归一化输入并重述原始信息

固定模板：

- 公历：XXXX 年 XX 月 XX 日
- 时间：XX:XX
- 性别：男或女
- 出生地：XX 省 XX 市 XX 区
- 争议点：如是否过子初、是否按后一天算

先判断用户给的是哪类排盘入口：

- 公历出生时间：直接归一化为 `--date YYYY-MM-DD --time HH:mm`。
- 已知四柱：归一化为 `--pillars "年柱 月柱 日柱 时柱"`，先调用问真“四柱”反推候选公历。
- 问真四柱反推不可用或需要交叉校验：用 `scripts/local_bazi_reverse_lookup.py` 获取本地候选，再把候选公历时间交给问真专业细盘脚本。

出生地处理规则：

- 用户给了出生地：用于估算经度并判断真太阳时是否影响时辰或日期。
- 用户没给出生地：不追问，不阻塞排盘；直接采用北京时间盘，并在输出中写明“未提供出生地，真太阳时不做经度修正，本轮按北京时间作为正式排盘时间”。
- 只有在用户主动补充出生地，或北京时间正卡在时辰/日期边界且用户要求严校时，才补跑真太阳时候选盘。

四柱反推出现多个候选时，默认采用中间候选作为初始排盘，理由是它通常更贴近现代常用时间范围。必须在输出里列出全部候选、默认采用哪一个、为什么这样默认。若用户明确指定候选编号、指定公历日期，或后续反馈“时间不对”，立即按用户意见重跑，不坚持默认候选。
如果问真和本地四柱反推返回的分钟不同，但日期和时辰相同，按同一候选处理，不把分钟差异当作候选盘分歧。

### Step 2：生成排盘底稿文件

先运行统一入口，默认问真优先、本地兜底。

最低命令格式：

```bash
python3 scripts/bazi_chart_fetch.py --source auto --date YYYY-MM-DD --time HH:mm --sex male|female --name NAME --output work/pcbz/<case-id>
```

四柱反推格式：

```bash
python3 scripts/bazi_chart_fetch.py --source auto --pillars "年柱 月柱 日柱 时柱" --sex male|female --name NAME --output work/pcbz/<case-id>
```

四柱反推时，脚本必须先保存 `raw/szbz.json`，并在 `chart.md` 输入区写明：

- 输入四柱
- 候选公历日期
- 最终采用的候选编号和时间
- 候选选择方式：默认中间候选，或用户显式指定候选

如果走本地兜底，脚本必须保存 `raw/local_lunar_python.json`，并在 `chart.md` 来源区写明：

- 排盘来源：本地 `lunar_python`
- 四柱反推来源：本地 `sxtwl.siZhu2Year`（仅四柱入口时）
- 问真失败原因（如果是自动兜底）
- 本地底稿缺少问真 raw、人元司令接口和问真格局接口

如果已经校正出真太阳时，要加：

```bash
--sun-time "YYYY-MM-DD HH:mm:ss"
```

如果涉及早晚子时争议，要分别运行：

```bash
--midnight 0
--midnight 1
```

每个候选盘单独保存到不同目录，例如：

- `work/pcbz/<case-id>/beijing-time/`
- `work/pcbz/<case-id>/true-solar-time/`
- `work/pcbz/<case-id>/midnight-0/`
- `work/pcbz/<case-id>/midnight-1/`

运行后必须检查 `chart.md` 的“后续分析必读”至少包含：

- 阴历/阳历
- 四柱
- 主星、天干、地支、藏干、副星
- 起运、交运、大运公历起止年份
- 按公历年份列出的流年干支索引

低优先级附录可包含：

- 星运、自坐、空亡、纳音、神煞
- 胎息、胎元、命宫、身宫
- 干支关系、格局接口结果

### Step 3：判断年柱、月柱

规则：

- 年柱按节气立春，不按春节
- 月柱按节气切换，不按农历初一

输出时明确写：

- 该生日处于什么节气区间
- 因此年柱为何、月柱为何

此步以 `chart.md` 和 `raw/getbasebz8.json` 为主证。

### Step 4：判断北京时间所属时辰

先不修正，按北京时间判定是否为亥时、子时、丑时等。

### Step 5：判断出生地经度与真太阳时

规则：

- 用户未提供出生地时，直接采用北京时间，不追问出生地，不生成真太阳时候选盘。
- 东八区中央经线为 120E
- 每相差 1 度经度，时间约差 4 分钟
- 出生地偏东则真太阳时更晚，偏西则更早

输出时写清：

- 未提供出生地时：写“未提供出生地，本轮不做真太阳时经度修正，按北京时间排盘。”
- 出生地经度约多少
- 比 120E 多或少多少
- 约折算多少分钟
- 因而北京时间校正为约多少真太阳时

如果真太阳时会影响时辰或日期，必须用 `--sun-time` 再跑一份问真专业细盘文件。

### Step 6：形成至少两套候选盘

最低标准按输入完整度决定：

1. 一定要有北京时间盘。
2. 用户提供出生地且真太阳时会影响时辰或日期时，再生成真太阳时盘。
3. 若存在后一天争议，再给出后一日盘。
4. 用户未提供出生地时，不为了真太阳时单独追问；直接采用北京时间盘，并记录这是因地点缺失做出的边界选择。

每套候选盘都要对应自己的 `chart.md`，不能只在文字里手动改柱。

### Step 7：明确争议真正落在哪里

要写清是年柱、月柱、日柱还是时柱争议。很多案例里真正有争议的是时柱，不是日柱。

### Step 8：给出最终采用盘，但保留候选盘以备验盘

结论格式：

- 正式采用：X 年 X 月 X 日 X 时
- 采用文件：`work/pcbz/<case-id>/<variant>/chart.md`
- 不采用：……
- 理由：节气、真太阳时、子时分法、前事验证路径

### Step 9：若候选盘仍未分胜负，转入流年模块

不在本模块里硬压结论，而是把分歧交给 `/bazi-liunian` 做前事和年份验证。

## 子时专项

### 适用场景

- 记录出生时间在 23:00 到 00:59。
- 出生时间接近 23:00 或 01:00，且出生地偏离 120E 较多。
- 用户问早子、晚子、子初换日、次日子时、今日明时。
- 出生地在四川、新疆、西藏、甘肃、云南、贵州、重庆等偏西地区，时间又接近子时。
- 出生日期在 1986 到 1991 年中国夏令时可能影响记录时间。
- 不同软件排出不同日柱或时柱。
- 用户只说“夜里子时”“23 点多”“大概 0 点左右”，时间可信度不足。

### 子时分层

必须区分：

- 记录时间：用户或出生证明上写的钟表时间。
- 标准北京时间：如遇夏令时，记录钟表时间可能要先减 1 小时。
- 真太阳时：按出生地经度校正后的自然时间。
- 子时归日：进入子时后，日柱按哪套口径切换。

真太阳时只判断时辰，不自动决定日柱。经度校正后是否入子时，是时辰问题；进入子时后是否换日，是子时分法问题。这两步不能合并。

若需要书证支撑“子时内仍存在归日分法”，先查本地《七修类稿》卷一“阳奇阴耦”条：`references/classics-originals/raw/七修类稿/卷一.txt`。该条可作为“夜分上下半、今日/明日口径不同”的传统材料，但不能替代候选盘加前事核验。

### 子时工具流程

先运行分诊脚本生成候选盘计划：

```bash
python3 scripts/zi_hour_triage.py --date 2000-05-01 --time 23:15 --sex female --name 命主 --birthplace 四川成都 --output work/zi-hour/<case-id>
```

如果知道精确经度，优先显式传入：

```bash
python3 scripts/zi_hour_triage.py --date 2000-05-01 --time 23:15 --sex female --name 命主 --longitude 104.0665 --output work/zi-hour/<case-id>
```

脚本输出：

- `zi_hour_report.json`：结构化分诊结果。
- `zi_hour_report.md`：人类可读报告。
- 候选盘命令：后续要逐条执行，生成每个候选盘的 `chart.md`。

每个候选盘必须生成：

- `chart.md`
- `chart.json`
- `raw/`

若候选盘差异仍未压缩，转 `/bazi-liunian`。给当事人的核验问题必须按 `references/momtest-validation-questions.md` 写成事实采集，不把候选盘画像、十神判断或年份暗示讲给当事人。

## 可复用判断规则

### 规则 A：先区分入子时和换日

- 入子时不等于必然换日
- 真太阳时修正后进入子时，也仍可能按前一日取日柱

### 规则 B：子时案例必须双轨呈现

凡涉及 23:00 左右出生：

- 必须给出至少两种排法
- 必须说明各自理论依据
- 不能偷换前提

### 规则 C：排盘阶段不做过度断语

此阶段最多只允许说：

- 哪套盘更值得进入验证
- 哪个争议点最关键

不允许在排盘未定时直接断“婚姻必离”“事业必成”等绝对结论。

### 规则 D：出生地越精确，真太阳时越有必要

尤其是：

- 东北、华南、边疆
- 大城市内不同区县一般影响不大，但省际差距会大
- 接近 23:00/01:00/03:00 等时辰边界时，地点精度很重要

但如果用户没有提供出生地，本模块不得停下来追问；先按北京时间完成排盘和分析边界说明。用户后续补充地点时，再补跑真太阳时盘。

### 规则 E：没有文件，不进入分析

排盘文件是后续分析的底稿。

- 没有 `chart.md`：先补跑脚本
- `chart.md` 缺四柱十神、藏干十神、大运起止年份、流年干支索引等关键段落：检查 raw 响应或重新请求
- 页面/API 失败：说明失败接口、HTTP 状态、错误文本和残余风险
- 不允许把浏览器页面截图、人工复制片段当成完整专业细盘

## 输出模板

### 模板 1：标准输出

> 先定盘，再论命。你的案例争议点不在年柱和月柱，而在“晚间出生是否因真太阳时进入子时，以及进入子时后是否换日”。
>
> 我会先给三套：
> 1. 北京时间盘：……（文件：`.../chart.md`）
> 2. 真太阳时盘：……（文件：`.../chart.md`）
> 3. 后一日候选盘：……（文件：`.../chart.md`）
>
> 然后告诉你：真正需要验证的是日柱还是时柱，以及我为什么暂时优先取哪一套。

### 模板 2：明确争议落点

> 这类命最容易错的不是年份，而是“23 点前后到底算不算换日”。
> 先说结论：你这个案例真正有争议的是 X 柱，不是 Y 柱。

### 模板 3：最终采用

> 正式分析我先采用：X 年 X 月 X 日 X 时。
> 但我保留 A 盘和 B 盘作为候选，并建议用学历、家庭、恋爱经历做反校验。

## 错误清单

- 把农历月份当作月柱依据
- 把进入子时和换到第二天直接画等号
- 不校正真太阳时就武断定日柱
- 只给一个盘，不展示候选盘与理由
- 排盘阶段就开始大量断前事，导致后续无法收口
- 用浏览器手动点页面却不保存专业细盘文件
- 绕过问真接口改用其他排盘源
